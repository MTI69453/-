**Самостоятельная работа № 3. Планирование ревьюирования программного проекта**

Проект: интернет-магазин «ShopCore» (Python, backend-сервис).
Изменение: новая версия модуля расчёта скидок `discounts` (ветвь `feature/discounts-v2`).

---

## 1. Объект и цель ревьюирования

### 1.1. Объект ревьюирования

Объектом ревьюирования является **программный модуль `discounts`** (новая версия), изменения которого находятся в ветви Git `feature/discounts-v2`. В состав изменений входят:

- функция `calculate_discount(order, customer)` — расчёт итоговой скидки на заказ;
- функция `validate_promo_code(code)` — проверка промокода;
- изменение публичного API: функция теперь возвращает объект `DiscountResult` (сумма скидки, применённые правила, причина отказа) вместо числа;
- модульные тесты в каталоге `tests/test_discounts.py`;
- обновлённая документация модуля (`docs/discounts.md`).

### 1.2. Почему объект требует проверки перед слиянием

- Модуль напрямую влияет на **денежные расчёты**: ошибка приводит к финансовым потерям (завышенная скидка) или жалобам клиентов (заниженная скидка).
- Изменён **формат возвращаемого значения**, а значит, могут сломаться модули, которые его вызывают (корзина, оформление заказа, отчёты).
- Модуль обрабатывает **данные от пользователя** (промокоды), поэтому требует проверки обработки недопустимого ввода и безопасности.
- Основная ветвь `main` используется для выпуска версий, и дефект, попавший в неё, будет дороже исправлять, чем на этапе ревью.

## 2. Цель ревьюирования

Цель — не просто «найти ошибки», а **оценить, готова ли новая версия модуля к включению в основную ветвь**. Для этого необходимо оценить следующие свойства реализации:

1. **Соответствие требованиям** — все правила скидок из ТЗ (скидка по сумме заказа, скидка постоянным клиентам, промокоды, ограничение максимальной скидки 50 %) реализованы.
2. **Корректность алгоритма** — расчёты верны, округление выполняется до копеек, результат не зависит от порядка применения правил.
3. **Обработка входных данных** — пустой заказ, отрицательные суммы, `None`, просроченный или несуществующий промокод обрабатываются предсказуемо, без падения сервиса.
4. **Отсутствие побочных эффектов** — функции не изменяют переданные объекты, не пишут в БД и не меняют глобальное состояние.
5. **Совместимость** — изменение API не ломает существующих вызывающих модулей.
6. **Тестируемость и покрытие тестами** — основные и граничные сценарии покрыты автоматическими тестами.
7. **Понятность и сопровождаемость кода** — понятные имена, отсутствие дублирования, комментарии и документация актуальны.
8. **Безопасность** — в коде нет секретов, нет небезопасной обработки пользовательского ввода.

## 3. Участники процесса

| Роль | Кто | Ответственность |
|---|---|---|
| **Автор изменений** | Разработчик модуля | Готовит ветвь, запускает локальные проверки, создаёт Pull Request (PR) с описанием, отвечает на замечания и вносит исправления |
| **Ревьюер** | Другой разработчик команды (не автор), знающий предметную область | Изучает diff, сопоставляет код с критериями, оставляет замечания, подтверждает исправления, выставляет решение (Approve / Request changes) |
| **Ответственный за автоматические проверки** | DevOps-инженер / разработчик, настроивший CI | Поддерживает конвейер CI (тесты, линтер, анализ секретов), следит, чтобы проверки были обязательными |
| **Ответственный за слияние (мейнтейнер)** | Технический лидер проекта | Проверяет выполнение условий допуска и выполняет слияние в `main`, разрешает конфликты слияния при необходимости |

Правило: **автор не может быть собственным ревьюером и не может сам выполнить слияние** своего PR.

## 4. План этапов ревьюирования

| № | Этап | Ответственный | Действия | Результат |
|---|---|---|---|---|
| 1 | Подготовка изменений | Автор изменений | Актуализирует ветвь (`git pull --rebase origin main`), перечитывает собственный diff, удаляет отладочный код, запускает локально тесты, линтер и форматтер, обновляет документацию | Изменения готовы к передаче, локальные проверки пройдены |
| 2 | Предварительные проверки | Автор / CI (ответственный за автопроверки) | Автор делает `git push`; CI автоматически запускает тесты, линтер (Ruff/Pylint), проверку типов (mypy), поиск секретов (gitleaks), измерение покрытия | Получен отчёт CI; при красном статусе PR не передаётся ревьюеру |
| 3 | Передача на ревью | Автор изменений | Создаёт Pull Request в `main`, заполняет шаблон описания (что изменено, зачем, как проверить, риски), назначает ревьюера | PR создан, ревьюер уведомлён |
| 4 | Изучение кода | Ревьюер | Читает описание и ТЗ, изучает diff по файлам, запускает ветвь локально, проверяет сценарии по списку критериев (раздел 5) | Составлено понимание изменения, выявлены потенциальные проблемы |
| 5 | Фиксация замечаний | Ревьюер | Оставляет комментарии к строкам кода в PR, расставляет приоритеты (blocking / non-blocking), завершает ревью решением *Request changes* либо *Approve* | Все замечания зафиксированы в PR; автор уведомлён |
| 6 | Исправление проблем | Автор изменений | Отвечает на каждый комментарий, вносит правки отдельными коммитами, делает `git push`, помечает обсуждения | Подготовлена обновлённая версия ветви, CI запущен повторно |
| 7 | Повторная проверка | Ревьюер | Просматривает только новые коммиты, проверяет, что каждое замечание закрыто, проверяет результаты CI и отсутствие регрессий | Подтверждено устранение замечаний (*Approve*) либо замечания возвращены |
| 8 | Принятие решения о слиянии | Ответственный за слияние (мейнтейнер) | Проверяет условия из раздела 11: одобрение, зелёный CI, закрытые обсуждения, отсутствие конфликтов | Изменения слиты в `main` (Squash and merge) либо возвращены на доработку |

| 5 | Отсутствие критических замечаний статического анализа | 0 ошибок уровня error в Ruff/Pylint и mypy; новые предупреждения обоснованы | Результат задания CI «lint» |
| 6 | Соблюдение правил оформления | Код соответствует PEP 8 и `pyproject.toml` проекта; нет неиспользуемых импортов и закомментированного кода | Ruff/Black в pre-commit и CI; визуальный просмотр diff |
| 7 | Отсутствие побочных эффектов и совместимость | Входные объекты не изменяются; все вызовы старого API в проекте обновлены | Поиск по проекту (`Find All References` в IDE); тест на неизменность входных данных |
| 8 | Безопасность | В коде нет паролей, токенов, ключей; промокод не используется в запросах без экранирования | Gitleaks в CI; просмотр diff ревьюером |

## 7. Фиксация замечаний

**Где фиксируются:** все замечания оформляются **в Pull Request на GitHub** (вкладка *Files changed*). Замечания в чатах и устных обсуждениях считаются неофициальными: если по ним принято решение, оно переносится в комментарий PR.

**Как замечание связывается с кодом.** Ревьюер выбирает строку или диапазон строк в diff и добавляет *Review comment*. Комментарий автоматически привязывается к файлу, строке и конкретному коммиту. При необходимости используется блок *suggestion* с готовым вариантом исправления.

**Приоритеты замечаний** (указываются префиксом):

- `[blocking]` — обязательно к исправлению, иначе слияние невозможно;
- `[non-blocking]` — рекомендация, исправление желательно;
- `[question]` — вопрос ревьюера, требует ответа;
- `[nit]` — мелкое замечание по оформлению.

**Как автор узнаёт о замечании:** GitHub отправляет уведомление по e-mail и в интерфейсе; PR получает статус *Changes requested*; расширение GitHub Pull Requests в VS Code показывает комментарии рядом с кодом.

**Как определяется, что вопрос рассмотрен.** Автор отвечает в ветке обсуждения и указывает коммит с исправлением. Обсуждение помечает *Resolved* ревьюер после проверки исправления (а не автор). Пока остаются неразрешённые обсуждения с пометкой `[blocking]`, слияние запрещено.

**Пример корректно сформулированного комментария ревьюера**

> Файл `discounts/calculator.py`, строка 47
>
> **[blocking]** В функции `calculate_discount` при `order.total == 0` происходит деление на ноль в выражении `discount / order.total` (строка 47), так что сервис упадёт с `ZeroDivisionError` при пустой корзине с промокодом. В ТЗ (п. 3.2) для пустого заказа должна возвращаться скидка 0.
>
> Предлагаю добавить проверку в начале функции:
> ```suggestion
> if order.total <= 0:
>     return DiscountResult(amount=Decimal("0.00"), reason="empty_order")
> ```
> И добавить тест `test_empty_order_returns_zero_discount`.

Комментарий хорош тем, что указывает точное место, описывает последствие, ссылается на требование, предлагает решение и обозначает приоритет.

## 8. Исправление выявленных проблем

1. **Анализ замечаний.** Автор читает все комментарии, при непонимании задаёт уточняющий вопрос в обсуждении. Если автор не согласен, он аргументированно отвечает в ветке; спорные вопросы решает мейнтейнер.
2. **Исправление в отдельных коммитах.** Автор работает в той же ветви `feature/discounts-v2`. Каждое замечание (или группа связанных) исправляется отдельным коммитом с сообщением вида:
   `fix(discounts): handle empty order in calculate_discount (review comment #1)`
   История ветви не переписывается (`force push` запрещён) на время ревью, чтобы ревьюер видел только новые изменения.
3. **Локальная проверка.** Перед отправкой автор снова запускает тесты, Ruff и mypy.
4. **Отправка.** `git push` обновляет PR; CI автоматически запускается повторно.
5. **Сообщение о выполненной работе.** В каждом обсуждении автор оставляет ответ: «Исправлено в коммите `a1b2c3d`, добавлен тест `test_empty_order_returns_zero_discount`». После завершения всех исправлений автор оставляет в PR итоговый комментарий и повторно запрашивает ревью (*Re-request review*).
6. **Подтверждение устранения.** Замечание считается устранённым только после того, как ревьюер проверил исправление и нажал *Resolve conversation*.

## 9. Повторное ревьюирование

Ревьюер проверяет не весь PR заново, а **изменения после первого ревью** (на GitHub — *Changes since last review*), однако с учётом их влияния на остальной код.

**Что проверяется:**

| Что проверить | Как убедиться |
|---|---|
| Исходная проблема устранена | Открывает коммит-исправление, повторяет сценарий из замечания (например, запускает расчёт для пустого заказа), проверяет наличие нового теста |
| Не появились новые ошибки | Просматривает diff новых коммитов; запускает полный набор тестов; проверяет смежные места (вызовы изменённых функций через *Find All References*) |
| Не нарушен стиль и типы | Смотрит результат заданий Ruff и mypy |
| Автоматические проверки соответствуют требованиям | В PR все обязательные проверки (tests, lint, mypy, gitleaks) имеют статус ✅; покрытие нового кода не ниже 85 % |
| Все замечания обработаны | Список обсуждений: нет неразрешённых `[blocking]`; `[non-blocking]` либо исправлены, либо обоснованно отклонены |

**Результат:**

- если всё выполнено — ревьюер ставит *Approve*;
- если проблемы остались или появились новые — возвращает PR на доработку (*Request changes*) с новыми комментариями, и цикл «исправление → повторная проверка» повторяется.

Если после ревью в ветвь влили изменения из `main` (из-за конфликтов), ревьюер дополнительно проверяет, что слияние не изменило логику модуля.

## 10. Правила доступа к репозиторию

| Роль | Чтение | Создание ветвей | Push в свои ветви | Открытие PR | Approve | Слияние в `main` | Прямой push в `main` |
|---|---|---|---|---|---|---|---|
| Автор (разработчик) | ✅ | ✅ | ✅ | ✅ | ❌ (в своём PR) | ❌ | ❌ |
| Ревьюер (разработчик) | ✅ | ✅ | ✅ | ✅ | ✅ (в чужих PR) | ❌ | ❌ |
| Ответственный за CI | ✅ | ✅ | ✅ (конфигурация CI) | ✅ | ✅ | ❌ | ❌ |
| Мейнтейнер | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| Администратор репозитория | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ (отключено правилами) |

**Защита ветви `main` (Branch protection rules):**

- прямой `push` в `main` запрещён всем, включая администраторов; изменения — только через Pull Request;
- для слияния требуется **минимум 1 одобрение** ревьюера (не автора); для изменений в `discounts/` — одобрение владельца кода по `CODEOWNERS`;
- обязательны успешные проверки CI (tests, lint, mypy, gitleaks);
- ветвь PR должна быть актуальной относительно `main`;
- все обсуждения должны быть разрешены;
- `force push` и удаление `main` запрещены;
- новые коммиты после *Approve* сбрасывают одобрение (*Dismiss stale approvals*).

**Правила безопасности:**

- запрещено передавать личные учётные данные (логины, пароли, токены) другим участникам, в том числе в комментариях PR и в чатах; доступ к репозиторию осуществляется только по личным учётным записям с двухфакторной аутентификацией и SSH-ключами;
- запрещено хранить секреты (пароли, API-ключи, токены) в исходном коде; они хранятся в переменных окружения и в *GitHub Secrets*; файл `.env` добавлен в `.gitignore`;
- включены *Secret scanning* и проверка `gitleaks`; при обнаружении секрета он считается скомпрометированным и немедленно заменяется, а не просто удаляется из кода;
- права выдаются по принципу наименьших привилегий.

## 11. Итоговое решение

### 11.1. Условия принятия изменений

Изменения допускаются к слиянию в `main`, **только если одновременно выполнены все условия**:

1. Устранены все существенные замечания (`[blocking]`), все обсуждения помечены *Resolved*; необработанные `[non-blocking]` замечания обоснованы или вынесены в отдельные задачи (issues).
2. Все обязательные автоматические проверки CI пройдены: тесты — 100 % успешных, покрытие нового кода ≥ 85 %, 0 критических предупреждений Ruff и mypy, gitleaks ничего не обнаружил.
3. Получено необходимое одобрение: минимум один *Approve* от ревьюера, не являющегося автором, и от владельца кода по `CODEOWNERS`.
4. Отсутствуют неразрешённые конфликты слияния, ветвь актуальна относительно `main`.
5. Обновлены документация и описание PR; в сообщении слияния указаны номер задачи и краткое описание.

Если хотя бы одно условие не выполнено, PR возвращается автору на доработку.

### 11.2. Вывод

Предложенный порядок помогает контролировать качество изменений на каждом этапе: от подготовки до включения в основную ветвь.

Ревьюирование не должно ограничиваться чтением исходного кода, потому что человек при просмотре легко пропускает рутинные дефекты (неиспользуемые переменные, ошибки типов, забытые секреты) и не может быстро проверить поведение кода на большом числе сценариев. **Автоматические проверки** (тесты, статический анализ, поиск секретов) берут на себя эту рутину и дают объективный результат, а ревьюер сосредотачивается на том, что машина оценить не может: соответствие требованиям, логика, читаемость, архитектура. **Управление изменениями** (Pull Request, защита ветви, роли и правила допуска) делает процесс воспроизводимым: никто не может слить код в обход проверки, а решение принимается по заранее известным условиям. **Повторная оценка исправлений** необходима, потому что исправление одной проблемы само по себе может внести новую; без повторной проверки нет уверенности, что замечание действительно устранено.

**Роль системы контроля версий и инструментов.** Git обеспечивает изоляцию изменений в отдельной ветви, точную фиксацию различий (diff), историю исправлений и возможность вернуться к предыдущему состоянию. GitHub превращает эти данные в процесс: Pull Request связывает код, комментарии и результаты проверок, а правила защиты ветви технически закрепляют условия допуска. VS Code ускоряет работу автора и ревьюера, Ruff, mypy, pytest и gitleaks автоматизируют проверки, а GitHub Actions гарантирует, что они выполняются при каждом изменении. Вместе эти средства образуют единый контролируемый путь изменения до основной версии модуля.
